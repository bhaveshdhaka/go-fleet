# WO-15 — Fresh-install path (no sos-lab, no hand curl)

> Owner directive 2026-08-28: full true-gap plan. A brand-new operator
> goes from bare repo → live public site with four verbs, every step
> journaled and machine-contracted:
> `site new` → `site tunnel create` → `infra deploy` → `site canary`.

## Decisions

- Scaffolding is CODE (embedded skeletons from the battle-tested live
  site templates), not docs: `site new` writes the same five templates
  the reference site runs, with the site namespace substituted.
- The registry skeleton carries DELIBERATE `TODO_*` markers — they pass
  validation (non-empty) while making every read verb show exactly what
  the operator still owes (account_id, zone ids). Self-documenting state.
- `site tunnel create` is the ONLY online step: one CF token, three API
  calls, tunnel token stored in the secrets home (never printed), ids +
  zone recorded by anchored registry edit + full revalidation.
- `site canary` reuses the cmdOps dispatch for ALL mutations (zero new
  mutation logic — the drill tests the product through its own front
  door). The build step runs --allow-dirty because the canary's own
  register dirties the tree; the drill is journaled end to end.
- QEMU fresh-site scenario DEFERRED with reasoning: the hermetic corpus
  (C16a-C16c) covers the verbs offline; the LIVE canary on hk-03-dev is
  the strongest fresh-install rehearsal that exists (real cluster,
  registry, CF). The remaining QEMU delta (bare-Ubuntu k3s install) is
  already owned by scripts/blocks/01-k3s.sh + BOOTSTRAP.md and cannot run
  inside this container. Revisit only if a fresh-box drill is actually
  needed.
